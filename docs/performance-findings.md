# postal-mime: базлайн производительности и варианты оптимизации

Методология: [performance-testing-plan.md](./performance-testing-plan.md). Харнесс: [`perf/`](../perf).

> **Статус: оптимизации из раздела 3 внедрены** (кроме 3.6, см. ниже). Итог первой волны —
> см. раздел 4; числа в разделах 1–2 сохранены как исторический базлайн «до».

Замеры: postal-mime 2.7.5, Apple Silicon (darwin arm64), Node v24.12.0,
Chromium 143–149 (playwright 1.57–1.61, vitest 3.2.4 и 4.1.10 дают совпадающие в пределах
шума числа), median по 10 итерациям (+3 warmup).
Полные данные — `perf/results/baseline.{node,chromium}.json`.

## 1. Базлайн

| Фикстура | Сценарий | Node, median | Chromium, median | Chromium медленнее |
| --- | --- | --- | --- | --- |
| full.eml (16.5 МБ, 11 влож.) | parse-default | 155 мс (101 МБ/с) | 204 мс (77 МБ/с) | +31% |
| full.eml | parse-attach-base64 | 339 мс (46 МБ/с) | 359 мс (44 МБ/с) | +6% |
| msg-attachments.eml (14.5 МБ, 4 влож.) | parse-default | 144 мс (97 МБ/с) | 177 мс (79 МБ/с) | +23% |
| msg-attachments.eml | parse-attach-base64 | 314 мс (44 МБ/с) | 324 мс (43 МБ/с) | +3% |

Наблюдения:

- **Гипотеза «в браузере медленнее» подтверждена**: +23–31% на дефолтном парсе, и в Chromium
  разброс заметно выше (rme ~8% против ~2% в Node).
- Опция `attachmentEncoding: 'base64'` делает парс **в ~2.2 раза медленнее** в обоих окружениях.

## 2. Что говорят CPU-профили

Self-time-топ (метод: `.cpuprofile` из `npm run perf:profile`, доли от семплированного времени;
в Node-профилях присутствует служебный фрейм `node:inspector.post` ~8–15% — артефакт семплера).

**parse-default, full.eml:**

| Функция | Node | Chromium |
| --- | --- | --- |
| `Base64Decoder.update` (src/base64-decoder.js:16) | 36% | 39% |
| `decodeBase64` (src/decode-strings.js:11) | 28% | 10% |
| `TextDecoder.decode` (нативный) | ~4% | **18%** |
| `readLine` (src/postal-mime.js:135) | 10% | 9% |
| garbage collector | 1–2% | **8.5%** |

**parse-attach-base64, full.eml:**

| Функция | Node | Chromium |
| --- | --- | --- |
| **garbage collector** | **40%** | **36%** |
| `Base64Decoder.update` | 14% | 18% |
| `decodeBase64` | 12% | 5% |
| `base64ArrayBuffer` (src/base64-encoder.js) | 4.5% | 8.4% |
| `parse`/сборка результата (src/postal-mime.js:438) | 11% | 7% |

Выводы:

1. **Доминирует декодирование base64-тел, и почти вся его стоимость — обвязка, а не декодирование.**
   `Base64Decoder.update` вызывается на каждую строку (~200k раз) и на каждой строке делает
   `TextDecoder.decode(line)` + regex `replace` + конкатенацию строкового remainder
   (src/base64-decoder.js:16-39). Собственно битовая работа (`decodeBase64`) — меньшая часть.
2. **Разница Node↔Chromium объясняется ценой вызова `TextDecoder.decode` на коротких строках**
   (18% против 4%) плюс GC-давлением. Это платформенный примитив: лечится не «настройкой браузера»,
   а сокращением числа вызовов.
3. **Сценарий attach-base64 упирается в GC**: `base64ArrayBuffer` строит строку через
   `base64 += …` на каждые 3 байта (~5.5M итераций на 16.5 МБ вложений) — 36–40% времени
   уходит в сборку мусора.

## 3. Варианты оптимизации (по убыванию эффекта)

Оценки эффекта — из долей self-time в профилях; проверять по протоколу: изменение →
`npm run perf` (сравнение с базлайном) → зелёный `npm test` (581 тест).

### 3.1. Байтовый путь в `Base64Decoder.update` — без TextDecoder и regex на строку

`src/base64-decoder.js:16-39`. Сейчас: байты строки → строка (TextDecoder) → regex-очистка →
строковый remainder → раз в 100 КБ `decodeBase64(строка)`. Предложение: остаться в байтах —
копить `Uint8Array`-чанки, отбрасывать не-base64 байты по таблице (уже есть паттерн в
`decodeBase64`), декодировать из байтов напрямую.

- Убирает: ~200k вызовов `TextDecoder.decode` (главная браузерная статья), regex-скан каждой
  строки, строковый remainder.
- **Ожидание: −35–50% на parse-default в Chromium, −25–35% в Node.** Самый большой выигрыш
  из всех пунктов.
- Риск: средний — переписывается ядро декодера; edge-cases (перенос групп через границы строк,
  паддинг, мусорные символы) покрыты существующими тестами.

### 3.2. Кодер вложений `base64ArrayBuffer` — без строковой конкатенации

`src/base64-encoder.js:19-46`. `base64 += a+b+c+d` на каждые 3 байта. Предложение: кодировать
кусками в предвыделенный массив/`String.fromCharCode.apply` по подмассивам и один `join`,
либо таблица пар символов.

- Убирает GC-доминанту сценария attach-base64 (36–40% всего времени).
- **Ожидание: сценарий attach-base64 приближается к parse-default (сейчас ×2.2).**
- Риск: низкий — изолированная чистая функция.

### 3.3. `readLine` через `TypedArray.indexOf` (memchr)

`src/postal-mime.js:135-158`. Ручной побайтовый цикл поиска `\n`. Предложение:
`this.av.indexOf(0x0a, readPos)` — нативный memchr.

- **Ожидание: −6–10% в обоих окружениях** (весь self-time `readLine`).
- Риск: минимальный, локальная замена.

### 3.4. Убрать по-строчный `await` в главном цикле

`src/postal-mime.js:472-476`: `await this.processLine()` на каждую из ~200k строк, хотя
асинхронность нужна только на границах MIME-частей (финализация через Blob). Предложение:
синхронный быстрый путь для обычных строк, `await` только на boundary/finalize
(или после 3.5 — полностью синхронный проход).

- **Ожидание: −3–7%** (микротаск-хопы размазаны по `(program)`/`task_queues`).
- Риск: средний — меняется управляющий поток парсера; важно не сломать публичный async-контракт.

### 3.5. Финализация декодеров без `Blob → arrayBuffer`

`src/base64-decoder.js:41-47`, `src/qp-decoder.js`, `src/pass-through-decoder.js`: чанки →
`new Blob(chunks)` → чтение обратно в `ArrayBuffer` — лишняя полная копия каждого вложения
(+async-хоп). Предложение: прямая сборка в предвыделенный `Uint8Array` (суммарная длина известна).

- **Ожидание: −3–5%, минус одна копия памяти на вложение** (важно для пиковой памяти в браузере);
  дополнительно развязывает 3.4.
- Риск: низкий; `Blob` в этом месте не является API-контрактом.

### 3.6. Не копировать весь вход на старте

`src/postal-mime.js:464`: `new Uint8Array(buf).buffer` — полная копия 16.5 МБ. Предложение:
работать поверх переданного буфера через byteOffset-aware view (осторожно: Node `Buffer`
шарит пул — нужен учёт `byteOffset/length`).

- Ожидание: единицы мс по времени, **−1 размер входа по памяти**.
- Риск: средний (алиасинг Buffer-пула, мутация входа пользователем).

### Сводная оценка

3.1 + 3.2 + 3.3 в сумме адресуют ~70–75% семплированного времени дефолтного сценария и
GC-доминанту base64-сценария; реалистичная цель после первой волны — **parse-default ≤ 80 мс
в Node (≥200 МБ/с) и ≤ 110 мс в Chromium**, attach-base64 — в пределах +20% к parse-default.
Порядок внедрения: 3.2 и 3.3 (низкий риск, быстрые победы) → 3.1 (главный выигрыш) →
3.5 → 3.4 → 3.6, с прогоном `npm run perf` и `npm test` после каждого шага.

## 4. Результаты внедрения (первая волна)

Каждый шаг: полный `npm test` (581 тест) + `npm run perf` в обоих окружениях; коммит только
при подтверждённом эффекте. Медианы full.eml::parse-default (Node / Chromium):

| Шаг | Коммит | Node | Chromium |
| --- | --- | --- | --- |
| Базлайн «до» | — | 159 мс | 199 мс |
| 3.2 кодер вложений без конкатенации | `f350c46` | 151 мс | 193 мс (attach-base64: −42…−53%) |
| 3.3 readLine → TypedArray.indexOf | `09c193e` | 156 мс | 158 мс |
| 3.1 байтовый base64-декодер | `1589ab8` | 65 мс | 67 мс |
| 3.5 сборка чанков без Blob | `14fab28` | 56 мс | 60 мс |
| 3.1б bulk-копия чистых base64-строк | `40414a7` | 43 мс | 47 мс |
| 3.4 без по-строчного await | `1424d30` | **28 мс** | **31 мс** |

Итог: **parse-default −82% Node (554 МБ/с) / −84% Chromium (510 МБ/с)**, attach-base64
−88% в обоих (теперь в пределах ~40% от parse-default при том, что сам parse-default стал
в 5–6 раз быстрее). Цели первой волны перевыполнены; разрыв Node↔Chromium сократился
с ~30% до ~10% — подтвердилось, что его создавали по-строчные вызовы `TextDecoder`.

**3.6 (вход без копии) — реализован, измерен и отклонён**: эффект по времени в пределах шума
(копия 16 МБ ≈ 1–2 мс), а защитное копирование входа — наблюдаемая семантика (мутация буфера
во время parse). Кандидат на возврат, когда в харнессе появится метрика пиковой памяти.

Базлайны в `perf/results/baseline.*.json` перезаписаны на состояние «после» — дальнейшие
прогоны ловят регрессии от нового уровня.

### Проверка на письмах меньшего размера

Добавлены три фикстуры без гигантских вложений: `attach.eml` (918 КБ, multipart/mixed,
2 вложения), `attach-inline.eml` (510 КБ, inline-картинка), `multipart.eml` (4.8 КБ,
multipart/alternative без вложений). Для файлов <1 МБ бенч использует 300 итераций
(см. `perf/bench-options.js`). Сравнение «до/после» (median, Node / Chromium):

| Фикстура | До | После | Эффект |
| --- | --- | --- | --- |
| attach.eml, parse-default | 9.3 / 9.0 мс | 1.8 / 1.8 мс | −80% |
| attach-inline.eml, parse-default | 5.1 / 5.2 мс | 1.0 / 1.1 мс | −79…−81% |
| multipart.eml, parse-default | 0.05 / 0.3 мс | 0.04 / <0.1 мс | −20% Node; в Chromium ниже пола таймера |

Выводы: на письмах с вложениями любого размера (0.5–16 МБ) эффект одинаковый —
−79…−89%, throughput стабильно ~350–530 МБ/с (узкие места были пропорциональны объёму
base64-тел). Крошечные письма без вложений упираются в фиксированный оверхед разбора
заголовков — там ускорение скромнее (−20%), а в Chromium медиана после оптимизаций
опустилась ниже разрешения `performance.now()` (0.1 мс), поэтому точная дельта не
измерима этим харнессом; `MB/s` для multipart.eml в отчётах показывает null по той же
причине.
