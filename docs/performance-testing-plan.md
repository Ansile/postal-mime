# Методология перформанс-тестирования EML-парсеров (JS)

Общий план фиксации и улучшения производительности JavaScript-библиотек, парсящих EML/MIME.
Применим к любой такой библиотеке (postal-mime, mailparser, letterparser, emailjs-mime-parser, …);
конкретная реализация для postal-mime живёт в [`perf/`](../perf), результаты разбора — в
[performance-findings.md](./performance-findings.md).

## 1. Цели

1. **Зафиксировать базлайн**: воспроизводимые числа парсинга тяжёлых писем в Node **и** в браузере
   (движки заметно различаются: у Chromium дороже `TextDecoder` и агрессивнее GC-профиль).
2. **Собрать CPU-профили** в обоих окружениях в едином формате.
3. **Подготовить оптимизации**: каждое предложение должно опираться на профиль, а не на интуицию,
   и проверяться сравнением с базлайном до/после.

## 2. Фикстуры

- **Реальные тяжёлые письма** (10+ МБ, multipart/mixed, десятки base64-вложений, ~200k строк) —
  синтетика не воспроизводит реальное распределение длин строк, заголовков и границ.
- **Анонимизация лёгким проходом с сохранением байтовой длины**: адреса и имена заменяются
  строками той же длины (для RFC2047/base64-вхождений — заменой base64-подстроки с совпадающими
  битами на границе группы). Структура, boundary, тела и размер файла не меняются, поэтому
  анонимизированный файл эквивалентен оригиналу по нагрузке. Скрипт: `scripts/anonymize-eml.js`.
- **Manifest с sha256 и размером** (`perf/fixtures/manifest.json`) — идентичность фикстур
  проверяема; результаты разных машин/библиотек сравнимы только на одинаковых фикстурах.
- В git фикстуры помечаются `*.eml -text` (`.gitattributes`) — иначе git нормализует CRLF→LF
  и молча ломает и байтовую идентичность, и MIME-семантику.

## 3. Харнесс

Стек: **vitest + `vitest bench` (tinybench) + Vitest Browser Mode (playwright/chromium)**.
Проверено: bench-режим работает в Browser Mode на vitest 3.2.x, включая `--outputJson`.
Версии раннера пиновать — benchmark-режим экспериментальный.

Разделение ответственности (единственный библиотеко-зависимый файл — адаптер):

```
perf/
  adapters/<lib>.js        # { name, capabilities, parse(bytes, options) } — всё специфичное здесь
  scenarios.js             # сценарии с capability-гейтами (не поддерживается — скипается)
  parse.bench.js           # матрица fixtures × scenarios
  bench-options.js         # параметры измерения
  harness/fixtures.js      # загрузка фикстур: fs в Node, fetch в браузере
  fixtures-plugin.js       # vite-middleware, отдаёт фикстуры браузеру мимо module pipeline
  harness/profiler.js      # withCpuProfile(): inspector в Node, CDP в браузере
  browser-commands.js      # Node-сторона CDP-профилировщика (vitest browser commands)
  report.js                # нормализация raw-результатов, сравнение с базлайном
  vitest.*.config.js       # node / browser / profile-конфиги
```

Ключевые решения:

- **Макро-бенчмарки**: одна итерация — сотни миллисекунд, поэтому tinybench управляется числом
  итераций (`iterations: 10, warmupIterations: 3, time: 0, warmupTime: 0, throws: true`),
  а не временем. Headline-метрика — **median**; throughput = размер / median.
- **Сценарии**: минимум «дефолтный парс» и по одному на каждую дорогую опцию библиотеки
  (например, `attachmentEncoding: 'base64'`); сценарии, которые библиотека не умеет
  (headers-only), объявляются с `requires` и скипаются по capability-флагам адаптера.
- **Фикстуры в браузер** отдаёт крошечный vite-middleware (`/__perf_fixtures__/*`) — 15-МБ бинарь
  нельзя пускать через модульный пайплайн Vite; загруженный `Uint8Array` переиспользуется между
  итерациями (парсер не должен мутировать вход — проверьте это для своей библиотеки).
- **Изоляция от основного тест-набора**: у vitest свои конфиги с явными `include`; файлы
  профилировщика не называть `*.test.js` — `node --test` рекурсивно подбирает такие файлы.

## 4. Базлайн и протокол сравнения

- `perf/results/baseline.<env>.json` — **коммитится**; `latest.<env>.json` и `raw.<env>.json` — нет.
- В отчёт всегда включаются метаданные: библиотека+версия, окружение, версия рантайма
  (node / chromium+playwright), ОС, CPU, git SHA, дата. Репортёр **громко предупреждает**,
  если текущая машина/рантайм не совпадает с базлайновой — дельты между разными машинами
  не значимы.
- Регрессии по умолчанию не роняют прогон (перф на dev-ноутбуке шумный); для CI есть
  opt-in порог `PERF_ASSERT_PCT=<n>`.
- Обновление базлайна — только явно (`PERF_UPDATE_BASELINE=1`), и никогда — из
  профилировочных прогонов.

## 5. CPU-профили

Единый формат **`.cpuprofile` (V8)** в обоих окружениях — открывается в Chrome DevTools
(Performance → Load profile) и speedscope:

- **Node**: `node:inspector` → `Profiler.enable/setSamplingInterval(100µs)/start/stop`.
  Не `--cpu-prof`: он профилирует весь воркер вместе с раннером и не даёт контроля границ.
- **Браузер**: кастомные vitest browser commands (Node-сторона) → `context.newCDPSession(page)` →
  те же `Profiler.*` через CDP. JS Self-Profiling API сознательно не используется
  (нужен `Document-Policy`-заголовок и конвертация формата).
- **Профилирование — отдельный прогон** (`profile.run.js`), не bench: семплер искажает тайминги
  на 5–15%. Один warmup-парс до старта профилировщика; старт/стоп строго вокруг итераций.
- Артефакты профилирования в профиле видны и известны: в Node — фреймы `node:inspector.post`,
  в обоих — фреймы раннера; фильтруются по именам функций библиотеки.

## 6. Анализ

1. Снять self-time-топ по каждому профилю (fixture × scenario × env).
2. Сверить Node против Chromium: расхождения указывают на разницу платформенных примитивов
   (типично: `TextDecoder`-вызовы, GC-давление от строкового мусора, `Blob`).
3. Смотреть не только на функции, но и на `(garbage collector)` — доминирующий GC означает
   аллокационную проблему (строковая конкатенация в цикле, тысячи мелких чанков), которую
   не видно в self-time самой функции-виновника.
4. Каждый кандидат на оптимизацию описывать как: подтверждение в профиле → изменение →
   ожидаемый эффект → риск. Проверка — тот же харнесс, сравнение с базлайном, и обязательный
   зелёный функциональный тест-набор.

## 7. Типовые горячие точки EML-парсеров (чек-лист)

По опыту разбора postal-mime — что искать в первую очередь в любой EML-библиотеке:

- **По-строчная обработка**: `TextDecoder.decode(line)` / regex на каждую из ~200k строк;
  `await` в цикле чтения строк (микротаск-хопы).
- **Base64/QP-декодеры**: накопление строкового remainder через `+=`, посимвольные циклы.
- **Финализация контента**: двойная материализация (массив чанков → `Blob` → `arrayBuffer`),
  копия всего входа на старте.
- **Кодирование вложений**: `result += chunk` на каждые 3 байта → GC съедает 30–40% времени.
- **Поиск конца строки**: ручной байтовый цикл вместо нативного `TypedArray.indexOf` (memchr).

## 8. Портирование на другую библиотеку

1. Скопировать `perf/` (без `fixtures/`, `results/`, `profiles/`).
2. Написать один адаптер `perf/adapters/<lib>.js`: `{ name, capabilities, parse(bytes, options) }`.
3. Указать на тот же корпус фикстур (sha256 в manifest гарантируют сопоставимость).
4. Node-only библиотека — просто не запускать browser-конфиги.
5. Прогнать `perf:baseline`, закоммитить базлайны — дальше сравнивать.

Результаты разных библиотек на одной машине и одних фикстурах сравнимы напрямую:
в JSON зашиты `meta.lib`, `meta.libVersion` и sha256 фикстур.
